## 🔴 1. Strategy places trades even when a position or pending order already exists

**Lines:** 473–502

sit inside the `if not open_position and not pending_order and

**Before (simplified):**
```python
if not open_position and not pending_order and not in_restricted_hours:

    ...create order...
elif self.signal == -1:
    ...create order...
```

**After (simplified):**
```python
if not open_position and not pending_order and not in_restricted_hours:
```

## 🔴 4. `filter_signals_profit` has TP/SL barrier logic reversed for long trades

**Files:** `ModelWorkbench/Learn/preprocess.py` and `Engine/Learn/preprocess.py`  
**Lines:** 344–358 (both files)

**The problem:**  
For `s == 1` (a long/buy trade), the function checks `if i['High'] >= sl` as
the stop-loss condition. But stop-loss on a long trade is triggered when the
**low** drops below `sl` (which is below entry price). Likewise it checks
`elif i['Low'] <= tp` for take-profit, but TP on a long is hit when the
**high** rises above `tp`. The long-trade conditions are using the Short
trade's OHLC extremes — they are completely swapped.

**What to change (in both files):**  
```python
# For s == 1 (LONG) — current code (WRONG):
if i['High'] >= sl:       # ← wrong: this is how short SL is detected
    ...stop loss...
elif i['Low'] <= tp:      # ← wrong: this is how short TP is detected

# For s == 1 (LONG) — corrected:
if i['Low'] <= sl:        # ← long SL: price falls below stop
    ...stop loss...
elif i['High'] >= tp:     # ← long TP: price rises above target

# For s == -1 (SHORT) — current code (WRONG):
if i['Low'] <= sl:        # ← wrong: this is how long SL is detected
    ...stop loss...
elif i['High'] >= tp:     # ← wrong: this is how long TP is detected

# For s == -1 (SHORT) — corrected:
if i['High'] >= sl:       # ← short SL: price rises above stop
    ...stop loss...
elif i['Low'] <= tp:      # ← short TP: price falls below target
```

> This function is not called by the current production training pipeline, but
> fix it in both files now to prevent it from silently poisoning any future
> analysis or filtered-label experiments that use it.

## 🟡 5. Model checkpoint selected on validation loss — primary objective is PnL

**File:** `ModelWorkbench/train_prod_model.py`  
**Lines:** 586–592

**The problem:**  
The training loop saves the "best" checkpoint whenever validation loss
improves. But the actual goal is positive cumulative PnL on the validation
set. It is common for a model to have a lower val loss at an epoch where PnL
is still negative, and a higher val loss at an epoch where PnL becomes
positive. The current logic can save the wrong checkpoint.

**What to change:**  
Change the checkpoint condition to save when **profit improves**, with
val-loss used only as a tiebreaker. If you want to keep val-loss as primary,
add a secondary save that also tracks the best-profit checkpoint separately and
logs both.

```python
# Option A: Save on best profit (recommended)
if eval_pack["profit"] > history.get("best_profit", float("-inf")):
    history["best_profit"] = eval_pack["profit"]
    history["best_epoch"] = epoch
    best_model_state = {k: v.detach().cpu().clone() for k, v in model.state_dict().items()}
    best_tag = " <-- best (profit)"
else:
    best_tag = ""
```

Also add `"best_profit": float("-inf")` to the `history` dict at line 530.

**Line:** 47

**The problem:**  
`COMMISSION = 0.00` means the "profit" metric used for checkpoint selection
and the PnL plot in `_plots.png` assumes zero trading costs. A model that
generates many marginal trades can show positive PnL during training but be

**What to change:**

a typical value is `0.00007` (0.7 pips expressed as a price fraction).
Each per-symbol launcher (`.train_<symbol>_<architecture>.py`) should set
this individually since costs differ by instrument.

correctly calls `causal_market_regime()` instead and does **not** have this

`triple_barrier_hilow_trend_labeler()` in both files:

```python

    """
    WARNING: This function uses a centered (non-causal) moving average
    and introduces lookahead bias. Do NOT use for training or feature
    generation. Use causal_market_regime() instead.
```

## 🟡 8. Resume-training overwrites the source model pack file — no safe-save pattern

**File:** `ModelWorkbench/train_prod_model.py`  
**Lines:** 648–706

**The problem:**  
When `RESUME_MODEL_PACK` is set, the training script saves the new model pack
back to the **same path** as the input file:
```python
model_pack_path = resume_model_pack_path if resume_pack else ...
```
If the process is killed or the disk fills up mid-write, the original model
pack is destroyed. There is no recovery.

**What to change:**  
Write to a temporary file first, then rename it atomically:

```python
import tempfile, shutil, pathlib

tmp_path = model_pack_path.parent / (model_pack_path.stem + "_tmp.pkl")
with open(tmp_path, "wb") as f:
    pickle.dump({...}, f)
shutil.move(str(tmp_path), str(model_pack_path))
```

This ensures the original file is only replaced after the write succeeds.

## 🟡 10. `preprocess_ohlcv` alignment is incorrect when `shift > 0` and interior NaN rows exist

**Files:** `ModelWorkbench/Learn/preprocess.py` and `Engine/Learn/preprocess.py`  
**Lines:** 39–197

**The problem:**  
The function does two `dropna()` passes. The first (line 42) removes rows with
NaN feature values. Then the target column is shifted (line 169) and a second
`dropna()` (line 174) removes rows where the shifted target is NaN (typically
the first `shift` rows). Finally, `X = X[shift:, :]` (line 177) crops X to
align with the dropped rows.

This alignment assumes the second dropna only ever removes rows from the
**start** of the array. If `shift > 0` and some rows were dropped from the
interior by the first dropna, the indexing `X[shift:]` will be off by the
number of those dropped rows.

Currently all production calls pass `shift=0`, so this does not trigger in
practice. However it is a latent bug if shift is ever changed.

**What to change:**  
After the second `dropna`, rebuild `X` from `df` directly rather than using
array-index slicing:

```python
# After the final df.dropna().reset_index(drop=True):
# Rebuild X from the surviving df rows to guarantee alignment
X = np.hstack([
    scaler.transform(df[scale_cols].values) if scale_cols else np.empty((len(df), 0)),
    df[passthrough_cols].values if passthrough_cols else np.empty((len(df), 0)),
    df[onehot_all].values       if onehot_all       else np.empty((len(df), 0)),
])
```

## 🟢 11. `donchian_trend()` and `time_in_trend()` use Python for-loops — very slow on large datasets

**Files:** `ModelWorkbench/Learn/features.py` and `Engine/Learn/features.py`  
**Lines:** 94–103 (`donchian_trend`), 108–116 (`time_in_trend`) — both files

**The problem:**  
Both functions iterate over every row with a Python `for` loop. On a 520-week
(~3.6M row) 1-minute dataset this takes several minutes each time features are
computed. NumPy vectorised equivalents run in milliseconds.

**What to change (both files):**

```python
# donchian_trend — vectorised replacement for the for-loop body:
trend_raw = np.zeros(len(df), dtype=int)
trend_raw[close.values > hh.shift(1).values] = 1
trend_raw[close.values < ll.shift(1).values] = -1
# Forward-fill zeros (hold last direction):
trend = pd.Series(trend_raw, index=df.index)
trend = trend.replace(0, np.nan).ffill().fillna(0).astype(int)
return trend.rename("donchian_trend")

# time_in_trend — vectorised using cumsum grouping:
change = trend_series != trend_series.shift(1)
group  = change.cumsum()
result = trend_series.groupby(group).cumcount() + 1
return result.rename("time_in_trend")
```

## 🟢 12. `BinaryTradeProfitabilityLoss` uses non-differentiable `argmax` inside the loss

**Files:** `ModelWorkbench/Learn/Loss.py` and `Engine/Learn/Loss.py`  
**Lines:** 226–250 (both files)

**The problem:**  
Inside `BinaryTradeProfitabilityLoss.forward()`, the profitability penalty
computes:
```python
pred_class = logits.argmax(dim=1)
trade_pred_mask = (pred_class == self.trade_class)
```
`argmax` has zero gradient everywhere (it is not differentiable). Masking by
`pred_class` means the profitability reward and SL penalty only apply to
samples where the model already "correctly" predicts a trade — samples near
the decision boundary get no gradient signal from this component. This makes
the profitability penalty almost invisible during early training when most
predictions are HOLD.

**What to change:**  
Replace the hard argmax mask with a soft probability-weighted mask so that
all samples receive a gradient proportional to how strongly the model is
predicting a trade:

```python
# Replace:
pred_class = logits.argmax(dim=1)
trade_pred_mask = (pred_class == self.trade_class)

# With:
p_trade = probs[:, self.trade_class]   # already computed above
# Use p_trade as a soft weight instead of a hard mask
```

Then weight the profitability score by `p_trade` directly rather than
filtering by `trade_pred_mask`.

## 🟢 13. `get_market_regime` regime-smoothing uses a forward-fill without a minimum-duration causal guard

**Files:** `ModelWorkbench/Learn/labels.py` and `Engine/Learn/labels.py`  
**Lines:** 353–354 (both files)

**The problem:**  
```python
df['Regime'] = df['Regime'].ffill().bfill()
```
The `bfill()` at the end propagates regime values **backward in time** for any
NaN values at the start of the series. Even though this function is already
flagged as non-causal (see item 7), the `bfill()` makes it worse and will
cause confusing behaviour if anyone runs analysis with it.

**What to change:**  
Replace `bfill()` with `fillna(0)` (treat unknown regime as range/flat):
```python
df['Regime'] = df['Regime'].ffill().fillna(0)
```
